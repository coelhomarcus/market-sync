TRABALHO 1 – SISTEMAS DISTRIBUÍDOS Engenharia de Requisitos e Desenvolvimento de um Agregador Concorrente Data da Apresentação 16/11/2026 Modalidade: Trabalho em grupo  Tecnologia: Python e sockets TCP Concorrência: Multithreading Avaliação: 6,0 pontos 1. CONTEXTUALIZAÇÃO Aplicações atuais, como plataformas de comparação de preços, buscadores de passagens, sistemas de monitoramento e agregadores de serviços, precisam consultar diferentes fontes de informação para apresentar resultados aos usuários. Essas aplicações frequentemente realizam várias consultas independentes, podendo executá-las simultaneamente para reduzir o tempo total de resposta. Neste trabalho, cada grupo deverá desenvolver uma aplicação baseada em comunicação cliente-servidor, capaz de consultar diferentes serviços independentes, consolidar os resultados e apresentá-los ao usuário. A atividade deverá integrar conhecimentos de Redes de Computadores e Sistemas Distribuídos, especialmente comunicação por sockets TCP, processos, threads e concorrência. Além da implementação, deverão ser realizadas atividades de Engenharia de Software, incluindo levantamento e análise de requisitos, modelagem, implementação, testes e documentação. 2. OBJETIVOS 2.1 Objetivo geral Desenvolver uma aplicação cliente-servidor que realize consultas concorrentes a diferentes serviços independentes, utilizando sockets TCP e multithreading. 2.2 Objetivos específicos • Aplicar técnicas de Engenharia de Software na especificação de uma aplicação. • Identificar atores, requisitos funcionais e não funcionais. • Elaborar diagramas de casos de uso e arquitetura. • Implementar comunicação entre processos utilizando sockets TCP. • Desenvolver um agregador capaz de realizar consultas sequenciais e concorrentes. • Utilizar threads para executar consultas simultaneamente. • Investigar os impactos da concorrência no desempenho. • Realizar experimentos e analisar resultados. • Documentar e apresentar o sistema desenvolvido. 3. ORGANIZAÇÃO DO TRABALHO O trabalho deverá ser realizado em grupo. Cada grupo sorteará um dos seis temas apresentados na seção seguinte. A aplicação deverá utilizar comunicação real por sockets TCP. Não será aceita uma implementação exclusivamente visual ou que simule a comunicação sem utilizar sockets. 4. TEMAS DOS PROJETOS TEMA 1 – COMPARADOR DE PREÇOS DE SUPERMERCADOS Desenvolver uma aplicação capaz de consultar diferentes supermercados e comparar preços de produtos. O sistema deverá permitir que o usuário informe um produto e receba os preços encontrados em diferentes supermercados. Funcionalidades mínimas: • Pesquisa de produtos. • Consulta a pelo menos quatro supermercados independentes. • Apresentação dos preços encontrados. • Ordenação dos resultados por preço. • Identificação do menor preço. • Comparação entre consultas sequenciais e concorrentes. Os supermercados poderão utilizar bases de produtos e preços simuladas. Possibilidade de evolução: comparação de cestas de compras e identificação do supermercado com menor custo total. 
5. ENGENHARIA DE SOFTWARE Antes da implementação, cada grupo deverá elaborar a especificação dos requisitos da aplicação. 5.1 Análise de requisitos O documento deverá conter: • Descrição do problema. • Objetivo do sistema. • Escopo. • Identificação dos atores. • Requisitos funcionais. • Requisitos não funcionais. • Restrições. • Critérios de aceitação. 5.2 Requisitos funcionais Cada grupo deverá especificar pelo menos oito requisitos funcionais. Exemplos: • RF01 – O sistema deverá permitir que o usuário informe os parâmetros de uma pesquisa. • RF02 – O sistema deverá consultar diferentes serviços independentes. • RF03 – O sistema deverá permitir consultas sequenciais. • RF04 – O sistema deverá permitir consultas concorrentes. • RF05 – O sistema deverá apresentar os resultados encontrados. • RF06 – O sistema deverá ordenar os resultados conforme um critério definido. • RF07 – O sistema deverá identificar a melhor opção segundo o critério escolhido. • RF08 – O sistema deverá registrar o tempo de execução das consultas. Os requisitos deverão ser adaptados ao tema escolhido. 5.3 Requisitos não funcionais Cada grupo deverá especificar pelo menos cinco requisitos não funcionais. Exemplos: • RNF01 – A comunicação entre os componentes deverá utilizar sockets TCP. • RNF02 – A estratégia concorrente deverá utilizar threads. • RNF03 – O servidor deverá atender múltiplas conexões simultaneamente. • RNF04 – O sistema deverá tratar falhas de comunicação. • RNF05 – A aplicação deverá permitir experimentos de desempenho. 5.4 Modelagem O grupo deverá elaborar: • Diagrama de casos de uso UML. • Diagrama de arquitetura da aplicação. • Diagrama de sequência de uma operação principal. Os diagramas deverão representar os componentes e os fluxos de comunicação. 6. ARQUITETURA DA APLICAÇÃO A aplicação deverá possuir, no mínimo, os seguintes componentes: Cliente: interface utilizada pelo usuário para realizar pesquisas. Agregador: componente responsável por receber as pesquisas, coordenar as consultas, consolidar resultados e responder ao cliente. Serviços independentes: pelo menos quatro servidores que representam as fontes consultadas. Cada serviço deverá executar como processo independente, podendo utilizar portas TCP distintas na mesma máquina. A arquitetura deverá permitir que o agregador consulte os serviços sequencialmente ou simultaneamente. 7. REQUISITOS TÉCNICOS A implementação deverá atender aos seguintes requisitos: 1. Utilizar sockets TCP para comunicação entre os componentes. 2. Possuir pelo menos quatro serviços independentes. 3. Implementar consultas sequenciais. 4. Implementar consultas concorrentes utilizando threads. 5. Permitir atendimento de múltiplos clientes. 6. Definir e documentar um protocolo de aplicação. 7. Implementar tratamento de erros e desconexões. 8. Registrar o tempo de execução das pesquisas. 9. Consolidar e apresentar os resultados. 10. Permitir demonstrar o funcionamento da aplicação durante a apresentação. A linguagem Python é recomendada. 8. PROTOCOLO DE COMUNICAÇÃO O grupo deverá definir um protocolo de aplicação para comunicação entre os componentes. Sugere-se a utilização de mensagens JSON transmitidas por sockets TCP. Exemplo de requisição: { "operacao": "consultar", "produto": "arroz" } Exemplo de resposta: { "fonte": "Fornecedor A", "produto": "arroz", "preco": 29.90, "status": "sucesso" } O protocolo deverá ser documentado, incluindo formato das mensagens, identificação das operações, tratamento de erros e encerramento das conexões. 9. EXPERIMENTOS OBRIGATÓRIOS Cada grupo deverá realizar experimentos comparando as estratégias sequencial e concorrente. Experimento 1 – Consulta sequencial Consultar todos os serviços um após o outro e registrar o tempo total. Experimento 2 – Consulta concorrente Consultar todos os serviços simultaneamente utilizando threads e registrar o tempo total. Experimento 3 – Simulação de latência Configurar atrasos artificiais nos serviços e comparar o tempo de execução das consultas sequenciais e concorrentes. Experimento 4 – Múltiplos clientes Executar pesquisas simultâneas a partir de diferentes clientes. Investigar o comportamento do agregador diante de várias solicitações. Experimento 5 – Indisponibilidade de serviço Desativar um dos serviços durante uma pesquisa. Investigar o comportamento do sistema e o tratamento da falha. Resultados O grupo deverá apresentar: • Tabelas de resultados. • Pelo menos dois gráficos. • Comparação entre as estratégias. • Discussão dos resultados. • Conclusões sobre multithreading. 10. ENTREGÁVEIS Cada grupo deverá entregar: Documento de requisitos: contendo análise, requisitos, atores, casos de uso e critérios de aceitação. Modelagem: diagramas de casos de uso, arquitetura e sequência. Código-fonte: implementação completa e instruções de execução. Relatório técnico: contendo introdução, requisitos, modelagem, implementação, experimentos, resultados e conclusão. Apresentação: slides e demonstração prática. 11. RESULTADO ESPERADO Ao final do trabalho, cada grupo deverá possuir uma aplicação funcional de agregação concorrente de consultas, acompanhada de documentação de requisitos, modelagem, implementação e análise experimental. O sistema deverá demonstrar que consultas independentes podem ser realizadas simultaneamente, permitindo investigar os efeitos da concorrência sobre o desempenho. A aplicação desenvolvida poderá servir como base para um projeto final mais abrangente de Sistemas Distribuídos, envolvendo integração de serviços, escalabilidade, cache, tolerância a falhas e novas estratégias de comunicação.
